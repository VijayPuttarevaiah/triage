01 Overview & Motivation

Modern cloud systems fail constantly: a bad deploy regresses a dependency, a connection pool wedges, a container leaks memory. The industry's default answer has been to page a human at 3 a.m., have them read three dashboards, guess a cause, and run a runbook by hand. Mean time to recovery (MTTR) in that model is dominated by human reaction time, not by the actual fix — the fix itself is usually a restart or a rollback that takes seconds.

Triage is an event-driven control plane that watches a production-style workload and, when an incident occurs, detects it via CloudWatch alarms, diagnoses it by gathering evidence and reasoning over it with a small LLM (Amazon Bedrock), governs the proposed fix through a policy engine that lives outside the LLM's reasoning loop, acts by executing the approved remediation, and learns by writing an immutable audit trail and an LLM-generated postmortem for every incident.

The system under protection, PayFlow, is a fintech-flavored transaction API. This choice is deliberate: fintech introduces a reliability constraint that a generic demo workload wouldn't have — a remediation that fires twice must never double-process a transaction. Idempotency is therefore load-bearing in the design (conditional writes keyed on transaction ID and incident ID, deduplication on alarm events), not decorative.

One-sentence narrative A Python control plane autonomously operates a Java workload — mirroring real enterprises, where AIOps tooling is almost never written in the same language as the systems it protects. Python's ~150 ms Lambda cold start sits directly on the incident-response critical path; the JVM's 2–6 s warm-up would not.

Across live testing on real AWS infrastructure (not a simulation — every number in §6 and §7 comes from actual CloudWatch alarms, actual Step Functions executions, and actual Bedrock calls), the system successfully diagnosed and closed the loop on all three designed failure scenarios, including one incident resolved via a fully organic EventBridge trigger with no manual intervention at all.

02 Functional Requirements

What the system does

  • PayFlow (workload plane): accepts and records transactions (POST /transactions, GET /transactions/{id}) with idempotent, conditional writes; exposes a health check; exposes fault-injection endpoints (/chaos/errors, /chaos/latency, /chaos/crash, /chaos/reset) used to demonstrate self-healing on demand.
  • Detection: three CloudWatch alarms (5xx rate, p99 latency, unhealthy host count) evaluate ALB/ECS metrics on a 1-minute period and route state changes through EventBridge.
  • Evidence gathering: a Lambda pulls the last 15 minutes of CloudWatch Logs Insights results, target-group metrics, and live ECS service/deployment state into one evidence bundle.
  • Diagnosis: a Bedrock (Nova Lite) call turns that evidence into a schema-constrained JSON diagnosis: probable cause, confidence, one recommended action name, and reasoning. The model can only ever name an action — it has no AWS credentials and cannot call any API.
  • Policy governance: a DynamoDB-backed allowlist decides, independently of the model, whether the named action is auto, needs_approval, or rejected, and enforces a per-action hourly rate cap.
  • Remediation: idempotent execution of one of three actions — force a new ECS deployment, scale out (capped at 2 tasks), or disable a feature flag (a rollback of last resort).
  • Human-in-the-loop approval: higher-risk actions pause the workflow (waitForTaskToken), send a plain-English email with one-click approve/reject links, and resume on click via an API Gateway callback.
  • Verification: a closed-loop check re-polls the triggering alarm on a bounded retry schedule before declaring the incident resolved.
  • Learning: every incident is written to an append-only DynamoDB audit trail and closed out with a Bedrock-generated markdown postmortem in S3, including measured MTTR.

04 Architecture Design & Diagrams

High-level architecture

Two planes, connected only through CloudWatch alarms and EventBridge — the agent plane observes and acts on the workload plane, but the workload plane has no knowledge of the agent plane at all (a real production boundary: PayFlow could be swapped for any other service without touching Triage's logic, as long as it emits the same three alarm shapes).

This traces the exact path exercised live on July 5, 2026: a chaos-injected error storm, auto-approved restart, and a closed-loop verification before the incident is marked resolved.

Design decisions worth defending

1. Policy enforcement outside the LLM's reasoning loop
Property
The blast radius of a hallucinated or manipulated diagnosis is bounded by a DynamoDB allowlist the model cannot write to.
Consequence
Automation is safe to run unattended for the two auto-approved actions; anything else is gated. Confirmed live: even when the model recommended the wrong action for the evidence (see §8), the policy engine's needs_approval gate meant nothing unsafe happened without a human clicking approve.
2. Idempotent remediation keyed on incident ID
Property
At-least-once delivery (Step Functions retries, duplicate alarm events) demands an idempotent consumer.
Consequence
A conditional UpdateItem on action_executed (false→true) gates every remediation; a duplicate invocation becomes a verified no-op rather than a double-restart or double-scale.
3. Dedup/cooldown at intake
Property
The agent itself needs a circuit breaker so a flapping alarm can't spawn parallel workflows.
Consequence
Intake queries a GSI for an OPEN incident on the same alarm within a 10-minute window before creating a new one. A real bug found in testing: the NotifyRejected path originally never closed the incident record out of OPEN, permanently blocking future alarms on that name — fixed by adding an explicit MarkRejected transition (see §6).
4. Closed-loop verification, not fire-and-forget
Property
A remediation isn't done until the alarm confirms it.
Consequence
A bounded Wait→Verify loop (originally 4×30s, widened to 8×45s after live testing showed CloudWatch's own evaluation window plus Fargate cold-start regularly exceeded the original 120s budget) escalates to a human via SNS instead of silently declaring victory.

06 Implementation

Repository & IaC coverage

Source is hosted at github.com/VijayPuttarevaiah/triage (private). 100% of AWS infrastructure is Terraform-managed — confirmed by running terraform plan after every live change throughout testing and getting No changes. Your infrastructure matches the configuration. every time. The only manual AWS action taken outside Terraform during the entire build was creating and then deleting a redundant IAM user during initial credential setup (superseded by an existing IAM Identity Center SSO profile) — it left no residual resource.

CI/CD — demonstrated live, not just configured

Two GitHub Actions workflows, both OIDC-authenticated:

  • payflow.yml — on push touching payflow/**: Maven test → build & push a linux/amd64 image to ECR → force a new ECS deployment.
  • triage.yml — on push touching agent/** or infra/**: ruff lint → pytest → terraform plan → terraform apply.

Both were run to completion multiple times against the real AWS account and returned green on every job (Set up job through Complete job), including a full Terraform apply cycle and a full Docker build/push/deploy cycle triggered purely by a git push.

Five real bugs found by live testing (and fixed)

  1. CloudWatch metric parameter bug: get_metric_statistics was always passed an ExtendedStatistics argument, even for non-percentile stats, where an empty list fails botocore's parameter validation.
  2. Wrong Bedrock model ID: anthropic.claude-haiku-4-5 requires an inference profile and rejected direct on-demand invocation; switched to amazon.nova-lite-v1:0, verified working via a direct Converse call before wiring it back in.
  3. Task-token URL encoding: Step Functions task tokens routinely contain +, which both API Gateway's parsed query params and Python's parse_qs silently decode as a space — corrupting the token and breaking every approval click. Fixed by parsing rawQueryString manually with unquote() (not unquote_plus()).
  4. Diagnosis prompt bias: the model twice recommended the high-risk rollback action (disable_feature_flag) for a plain latency symptom, apparently pattern-matching on the word "flag" in a log line. Fixed by tightening the system prompt's action-selection guidance and re-verified with a clean live run that then correctly chose scale_out.
  5. Rejected-path dedup bug: the NotifyRejected branch never updated incident status, permanently blocking dedup for that alarm. Fixed with an explicit MarkRejected state.

All five were found only because the system was deployed and exercised against real AWS — none would have surfaced from a code review alone. This is also why the approval-email UX issue reported after initial deployment (a single unreadable paragraph with a raw task token inline) was caught and fixed the same way: by looking at the actual email that arrived, not just the code that generated it.

The large majority of this project's code — all Terraform (network, compute, data, IAM, observability, agent plane, CI/CD OIDC), all 10 Python Lambda handlers, the Step Functions ASL definition, both GitHub Actions workflows, and the pytest suite — was generated with Claude Code (Anthropic), under direct human direction and with every claim in this report backed by live verification the author reviewed in real time (execution histories, CloudWatch metrics, actual emails received, actual CI run logs). 07 AWS Well-Architected Framework

Operational Excellence

Decisions: Infrastructure-as-code with a mandatory terraform plan before every apply (used throughout live testing to confirm zero drift); an immutable, queryable incident audit trail in DynamoDB; an auto-generated postmortem per incident so operational learning doesn't depend on someone remembering to write one up.

Trade-off: Local Terraform state committed to the repo is operationally simpler for a single operator but doesn't support concurrent applies safely — the documented production fix is an S3 backend with DynamoDB locking (§8).

Security

Decisions: Ten distinct per-Lambda IAM roles, each scoped to exactly the actions and resources that function needs (spot-checked live: remediate's role can touch only the triage-incidents table and the payflow ECS service, nothing else); GitHub OIDC federation so CI/CD never holds a static AWS key; S3 bucket versioning plus a full public-access block (all four flags) confirmed via get-public-access-block; the deploy operator authenticates via IAM Identity Center SSO, not a root or static-key IAM user — the account's default root credential was identified and deliberately avoided for every infrastructure action after discovery.

Trade-off: Chaos-injection endpoints on PayFlow (/chaos/*) are intentionally unauthenticated for demo convenience — acceptable because the ALB is the only ingress and the project is short-lived, but explicitly not a production pattern; a real deployment would gate these behind auth or remove them entirely in favor of AWS Fault Injection Simulator.

Reliability

Decisions: idempotent remediation via conditional DynamoDB writes; a closed-loop verify step so "resolved" is confirmed, not assumed; a dead-letter queue for any state-machine failure, with a real FAILED incident in the audit trail proving that path was actually exercised, not just designed.

Trade-off: the current design runs PayFlow at a single steady-state task by default; a production system would run ≥2 tasks across AZs at all times rather than relying on scale_out as a remediation action to reach that state reactively.

Performance Efficiency

Decisions: Python for the whole agent plane specifically because Lambda cold-start latency sits on the critical path; a small, on-demand Bedrock model chosen because the diagnosis task is classification-shaped, not open-ended — deliberately not reaching for a larger, slower, more expensive model that would add latency without adding correctness for this task shape.

Trade-off: Fargate sized at 0.25 vCPU/0.5GB keeps cost low but was directly responsible for the ~50s JVM cold-start that drove the MTTR NFR revision in §3 — a concrete, measured performance/cost trade-off, not a hypothetical one.

Cost Optimization

Decisions: on-demand DynamoDB billing, 3-day CloudWatch log retention, no NAT gateway (public-subnet Fargate tasks with security-group-scoped ingress instead), serverless agent plane with zero idle compute cost. Measured actual spend: $0.46 of a $100 credit after a full day of live infrastructure testing, with two budget alarms ($20/$50) as a backstop.

Trade-off: no NAT gateway means Fargate tasks get public IPs directly rather than routing through a NAT in a private subnet — cheaper and simpler for this project, but not the production-grade network isolation discussed in §8.

Sustainability

Decisions: a serverless-first control plane means zero compute runs when there is no incident to process — the agent plane's carbon and cost footprint scale with actual incidents, not with provisioned capacity. On-demand DynamoDB and 3-day log retention similarly avoid holding idle storage/capacity that would otherwise sit provisioned and unused.

Trade-off: PayFlow's ECS tasks run on x86_64 (linux/amd64), not Graviton/ARM64 — chosen because the fastest path from a local Apple Silicon dev machine to a working Fargate deployment was docker buildx build --platform linux/amd64 (in fact, the very first deployment attempt failed with a platform-mismatch error before this was made explicit — see §6). A production migration to Graviton-based Fargate would very likely reduce both cost and energy per request for the same workload; it was not pursued here given the report deadline.

08 Limitations & Production Roadmap

What's real IAM (already implemented)

Unlike a typical AWS Academy Learner Lab constraint, this project ran in a personal AWS account with full IAM control — so the least-privilege per-function roles, the GitHub OIDC provider, and the IAM Identity Center SSO setup described in §6/§7 are genuinely implemented, not merely discussed as a future intention.

What's still gapped for production

  • Terraform state: local state committed to a private repo. Fix: S3 backend + DynamoDB lock table, so CI and a human operator can never race each other.
  • Networking: default VPC, public subnets, no NAT gateway. Fix: private subnets for ECS tasks with VPC endpoints for DynamoDB/S3/ECR, behind a NAT gateway or (cheaper) gateway endpoints where available.
  • Bedrock guardrails: the diagnosis prompt is the only thing constraining model output today (enforced by strict JSON parsing + a hard fallback to none/escalate on any parse failure). Fix: Bedrock Guardrails as a second, independent layer.
  • Single region: no cross-region failover for either plane. Acceptable for a class project; a real fintech workload would need at least an active-passive secondary region.
  • Chaos realism: in-memory chaos flags mean a restart always genuinely cures the injected error storm — an elegant accident that keeps the demo honest, but real production failure modes (data corruption, downstream dependency outages, resource exhaustion) are not always restart-curable the way this simulation is. This is the single biggest gap between what was demonstrated and a real production incident.
  • Approval UX: now a readable plain-text email (fixed after direct user feedback on the raw version); a production system would likely use a Slack app or PagerDuty integration instead of email links for faster human response.
  • Diagnosis prompt robustness: the model's sensitivity to incidental wording (documented in §6) suggests a production system would want either a larger evaluation set of held-out incident transcripts to regression-test prompt changes against, or a hybrid rules-first/LLM-fallback diagnosis approach for the highest-confidence, most common failure shapes.

Priority order if continuing past this submission

  1. S3 Terraform backend + DynamoDB locking (closes the CI/local-state race gap identified in §5/§6).
  2. Bedrock Guardrails on the diagnosis call.
  3. Private subnets + VPC endpoints.
  4. Graviton/ARM64 migration for the sustainability trade-off noted in §7.
  5. A held-out test set of incident transcripts to regression-test diagnosis-prompt changes before they reach production.
